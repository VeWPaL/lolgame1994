# 1. THE STUTTER: CAUSE, FIX, PROOF
===================================================================================================

## The symptom

Reported as "very stuttery, unplayable" in normal gameplay.

## Why the obvious measurements were useless

The first four measurements I took all said the game was fine:

| measured                                   | result  | verdict      |
|--------------------------------------------|---------|--------------|
| tick cost, 27 bodies, sound live          | 0 ms    | fine         |
| frame interval, RAF-sampled, 200 frames    | 3.6 ms median, 7.4 p95 | fine |
| same, with the weapon bench open           | fine    | fine         |
| same, sound muted                         | fine    | fine         |

All four were wrong, and they were wrong for one reason: **headless Edge suspends the AudioContext.**
`play()` checks `ctx.state==='running'` and returns before building anything, so every benchmark
measured the silent path. The code I was profiling was not the code that was running on the player's
machine. This is worth stating as a rule: in this project, a headless audio measurement measures
nothing.

## The cause

Three faults in `src/45-sound.js`, compounding.

**1. Only the source of each sound was tracked and stopped.** A sound is 3-6 nodes: an oscillator or
buffer source, a gain, sometimes a filter, and a StereoPanner for anything panned. `track()` was
given one node. So a panned hit left its panner, filter and gain connected to the master graph for
the life of the page - no upper bound, nothing ever reclaiming them.

**2. `prune()` reclaimed by asking the audio clock.** `ctx.currentTime` only advances while the
context is RUNNING. On a suspended context it is frozen, so `now > v.__end` was never true and
nothing was ever reclaimed. The list grew by 3-6 nodes per shot with nothing removed, and because
`play()` walked it on every trigger pull, the cost was quadratic in the length of the fight. The
suite run that exposed it had played 86,606 sounds and stopped responding entirely.

**3. The reservation counter grew without bound.** `reserved++` per play, decremented only by
`releaseOldest()`. Past the cap, every sound paid a full scan of a list that never shrank.

There is also a conceptual error underneath all three: **a sound is 3-6 NODES, so the cap was
counting the wrong thing.** Comparing "sounds reserved" against "nodes live" counted two different
quantities, and releasing one per play released fewer nodes than a single sound adds.

## The fix

- Every node a voice creates is tracked, via factories (`T.osc()`, `T.gain()`, ...) that a voice
  body cannot forget to call.
- The bound is enforced **structurally**: `trimToCap()` after each build, oldest first. The audio
  clock is only used to release things early. Correctness does not depend on the clock.
- The reservation counter is gone. There is one bound, on nodes, and it is 48 - roughly 8-16
  simultaneous sounds, which is the right number for a fight.
- Offline render nodes are excluded from the live pool (`tracking` flag).

## The proof

Measured with `--autoplay-policy=no-user-gesture-required`, so the context really is running:

    40,000 sounds played
    node count:  4 -> 48 -> 48 -> 48 -> 48 -> 48   (pinned at the cap, flat)
    cost:        0.27 ms per play, flat across the whole run

Before the fix, the same probe never returned.

# 2. A MEASUREMENT THAT LIED: THE OFFLINE RENDER RACE
===================================================================================================

## The symptom

A 90 ms `shot` reported a tail of 0.78 to 1.28 at 0 to -2 dBFS - a sound that is silent after
75 ms. The number moved between runs and between viewports: it passed at 1280x720 and failed at
960x600, repeatedly.

## Three wrong fixes

Each was reasonable, each was aimed at the **live** audio graph, and the live graph was innocent.

1. **Serialise the renders.** `Promise.all` over 12 renders corrupted each other, because
   `renderVoice` swaps the module's `ctx`. Serialising was genuinely necessary - just not sufficient.
2. **Clear the pool before rendering.** Necessary, not sufficient.
3. **Suspend the live context around each render.** This "worked" in that the suite stopped hanging,
   and it was the *reason* the suite hung: a suspended context never calls back on `resume()` in a
   headless browser with no audio device, so the `await` never settled. My own 20 s watchdog was what
   finally named the test.

## The actual cause

`renderVoice` builds its voice by swapping the module's `ctx` to an `OfflineAudioContext`, and then
**awaits `startRendering()`**. That await yields the main thread. The game's own code runs in the
gap - a fight loop, a keydown, another `play()` - and every one of those calls built its nodes
against the **offline** context and got rendered into the buffer being measured.

So the "shot" was a recording of whatever else happened to be sounding. That is why it was loud,
why it rang on, and why the number depended on interleaving rather than on the voice.

## The fix and its proof

One line: `play()` declines to build while a render holds `ctx`.

There is now a permanent test that fires **3,000 sounds into the render's await window**, because
the suite's own ordering made the real interleaving impossible to reproduce. That test:

    with the guard:     peak 0.0771, tail 0, identical across 4 trials
    guard mutated out:  peak 1.07, 500 ms ring, on every trial

The mutation result is the diagnosis stated as a number: a 90 ms shot that peaks over full scale
and rings for half a second, because it is not the shot.

This test is worth more than the fix. Every previous version of this assertion passed for the wrong
reason, and the file now records that history rather than just the conclusion.

# 3. update() SPLIT INTO FOUR PHASES
===================================================================================================

## Why

`update()` was 1,212 lines, and the C# port has to be written against it. A port cannot be written
or reviewed as one 1,200-line function. The split is the precondition for the remaining port work,
not a readability preference.

## Where the seams are

Chosen where the **data stops flowing**, not where the comments were. Measured before splitting,
by scope analysis over comment-stripped code:

| phase             | top-level names | reads a local of the phase before it |
|--------------------|-----------------|--------------------------------------|
| `tickPlayer`       | 14              | -                                    |
| `tickProjectiles`  | 2               | no                                   |
| `tickBodies`       | 15              | no                                   |
| `tickRoom`         | 2               | no                                   |

After splitting, a static check over all four phases confirms zero cross-phase local reads.

## Two shared values, dealt with explicitly

**`r`, the current room.** A local of `update()` that every phase read. Each phase now takes its own
from `currentRoom()` - the same object, so a change of name and not of behaviour. Worth recording:
the first attempt shipped a build where `tickBodies` threw `r is not defined` on the first tick,
and the static check that would have caught it did not exist yet. It does now.

**The player's lagged hitbox.** This one is a genuine handoff and could not be re-derived without
changing behaviour. The gunner intercept solves against `hitbox`, the position the player is
*visually leaving*, not `player.x` - that is the entire reason the intercept reads as leading rather
than chasing. It now goes through a named module value with the reason attached, because a local is
invisible to the phase that needs it.

Also worth noting: the same regex that moved `hx`/`hy` silently broke three boss helpers, which read
the player's **real** position and must not lead the visual one. Those were restored with a comment
explaining why they differ. This is the second time in this session that a mechanical rename produced
a silent behaviour change rather than an error, which is an argument for the scope check rather than
against the refactor.

## Result

    update()           93 lines   gates and dispatch
    tickPlayer()      169
    tickProjectiles() 160
    tickBodies()      697
    tickRoom()        109

Phase order unchanged and already pinned by `csharp/Depths.Tests/TickOrderTests.cs`: player,
projectiles, bodies, room, with a door transition aborting the rest of the tick - which is why
`tickPlayer` returns a boolean instead of `update()` returning from mid-body.

JS 236/237 at 1280x720 immediately after, with the one failure being the unrelated sound race.

# 4. THE TEST HARNESS WAS LYING TOO
===================================================================================================

Three separate defects in `src/99-tests.js`, all of which made a passing suite meaningless.

**Async verdicts were recorded before the assertions ran.** The harness called `fn()`, took the
returned promise, and pushed `{ok:true}`. Every assertion in an async test ran *after* its verdict was
recorded. The suite reported a green waveform check that had never looked at a waveform - and the
mutation that proved it, a voice made to ring for three seconds, passed.

**`settled` was written to an object that immediately ceased to exist.** `window.__testResults` is
REPLACED by an object literal, so a `settled` property assigned afterwards was gone. A probe waiting
on `settled===true` waited for ever on a suite that had already finished - at every viewport, on
green code. This one cost real time: I spent several rounds bisecting the game for a hang that was in
the reporting.

**No watchdog.** A promise that never settles hung the whole suite with no output at all. Each test
now races a timeout and is reported by name. The watchdog immediately earned its place: it is what
turned "the suite hangs" into "the sound test never finished".

One correction to my own reasoning: I first concluded the 20 s watchdog was firing on a legitimately
slow test. It was not - the sound test takes ~60 s of legitimate work (4,200 ticks plus 16 offline
renders). The watchdog is now 90 s, and the diagnosis came from timing the phases rather than from
raising the limit blindly.

# 6. POST-FIX PROFILING: WHERE THE TIME ACTUALLY GOES
===================================================================================================

All measured with the sound path genuinely LIVE (`--autoplay-policy=no-user-gesture-required`, so
`ctx.state === 'running'` and `play()` actually builds). The earlier benchmarks in this report were
taken on the suspended path and are retained above as the record of why they were worthless.

## Frame budget, per frame, at 27 bodies

    update()          0.039 ms
    render()          0.258 ms
    advance()         0.017 ms
    ------------------------------
    game work         0.314 ms   of a 16.67 ms 60fps budget  =  1.8%

The remaining ~3.2 ms is the browser compositing the canvas. It is not the game's, and it is not
optimizable from here - the floor for a bare RAF on this page is 0.9 ms with nothing drawn at all.

## Frame intervals, measured by RAF, in real fights

    bodies   frames   median   p90    p99    max   >33ms   >50ms
         5      259     3.6    4.0    4.6    7.0       0       0
        27      259     3.6    4.4    4.8    5.8       0       0
        50      259     3.7    5.4    9.0   15.6       0       0

Zero dropped frames at every body count. That is the stutter report answered in the game's own
terms: not one frame longer than a single 33 ms vsync interval, including at 50 bodies and 155
projectiles with the sound pool saturated.

## Heap, across a 4,200-tick fight

    3.76 MB at tick 0
    3.76 MB at tick 600, 1200, 1800, 2400, 3000, 3600
    3.76 MB peak, 4.02 MB after a forced collection

Flat to two decimal places for the whole fight. Nothing accumulates, so there is no collection pause
and no GC stutter. The FX pools (`burstFX`, `dashFX`) both drain to 0. This closes the second
classic cause of stutter-after-a-few-minutes: the game does not leak, and did not.

## The projectile loop is LINEAR, not quadratic - checked because it looked quadratic

`tickProjectiles` contains three `for(j=r.enemies.length...)` loops inside its per-projectile loop,
which is the textbook shape of an O(projectiles x bodies) hot spot. Bodies fixed at 27, projectiles
injected directly and parked away from every body so the inner loops iterate without colliding:

    projectiles    median    ratio vs previous
                0.1 ms
              100    0.2 ms
              300    0.3 ms
              600    0.6 ms
             1200    1.2 ms      2.0x for 2x the projectiles

Quadratic would give ~4x. It gives 2.0x. The inner loops reject on a cheap distance test before
doing any work, so there is no quadratic term to remove and a spatial hash would be complexity
without a measurement behind it. **Not changed**, and the reason is written down here so the next
person does not "optimise" it on the strength of the loop shape alone.

Note the fixture work this cost: three earlier attempts produced `live: 0` because the injected
projectiles were immediately culled - once by spawning them on top of the player where they hit a
body, once by omitting `from`/`dx`/`dy` from the object literal. Only measuring `projectiles.length`
after the run caught that. A benchmark that reports a flat line because its fixture is empty is
indistinguishable from a benchmark that found no problem.

## What this rules out, and what remains

Ruled out by measurement, not by argument: the tick, the renderer, allocation, GC, the projectile
loop, and the sound pool. Together they are the whole per-frame cost of the game at 1.8% of budget.

Not measured here, and genuinely open:
  - **The Unity/`.exe` path.** These numbers are a browser canvas. The same logic under Unity's
    renderer is a different budget with different hot spots, and `Tick.Update` still needs the four
    phases ported before any of it can be compared.
  - **Sustained long-session behaviour.** 4,200 ticks is 20 seconds. A 40-minute run is 50,400, and
    the heap being flat over 20 seconds is evidence, not proof, over 40 minutes.
  - **The player machine specifically.** Headless Edge on this host. A real GPU, a real audio device
    and a real browser compositor are all different - which is exactly the mistake that made the
    first four benchmarks in this report worthless, and the reason the next step is the user
    playtesting rather than another number from me.

# 7. A 45-MINUTE RUN: 960,001 TICKS, TWO FLOORS, ZERO THROWS
===================================================================================================

The 4,200-tick measurements above are 20 seconds of game time. This is the long-session question
that section 6 listed as open.

    ticks            960,001        (45 minutes of game time at 21 ticks/second)
    floors           1 -> 2, via a real boss kill and a real descent
    rooms            24 entered
    enemy types      lunger, shooter, gunner, brunch, boss   (all five)
    throws           none
    sound            pool never exceeded 48/48, 0 failed, 0 skipped

Heap through the run, sampled every 10 rounds:

    4.37 -> 6.45 -> 8.55 -> 9.66 -> 10.29 -> 8.56 -> 10.84 -> 9.17 -> 11.44 -> 9.71 -> 11.96 MB

That is a sawtooth, not a ramp: it rises, falls when a collection runs, rises again. It ends at
~12 MB after 45 minutes against ~4 MB at the start, and the rise is bounded - the same shape at
round 40 and at round 100. No monotonic growth, so nothing accumulates. This is what a healthy
long session looks like, and it is the evidence that was missing for "does it degrade over time".

## Three fixture defects found while building this, each of which had looked like a game defect

Worth listing, because each one cost real time and each produced a confident false conclusion:

**1. It never left the start room.** The first version steered with movement keys toward a door and
ran 50,400 ticks with zero enemies, zero rooms and zero projectiles, and reported `threw: null`. That
is a clean result from a fixture that exercised nothing. Rooms are now entered explicitly, the
technique the test suite already uses, and coverage is reported in the output so a vacuous pass
cannot be read as a clean one.

**2. `descends: 0` looked like a broken progression.** It is not: the exit portal only opens when a
BOSS dies, and the first boss is behind a gold key that only a boss gives. There is no legal path
from floor 1's start room to a descent, so a probe that respects the lock can never descend. Giving
the probe the key is the same shortcut the game grants.

**3. The boss "could not be killed" - 463 HP, 0 damage in 1,600 ticks.** Also the fixture: the probe
fought the boss with the starting weapon and no build, where a player arrives with one. With
`weaponIdx` and a damage bonus it dies, opens the exit, and is walked into, which is the whole
descent path.

The pattern across all three is the same one this file keeps arriving at, and it is now the single
most expensive mistake in the project: **a fixture that does not exercise the code reports success.**
The discipline that actually works is reporting coverage alongside the result - enemies seen, rooms
entered, floors reached, kills landed - so a run that tested nothing cannot pass for a run that found
nothing.

# 8. WHERE THE REMAINING WORK IS
===================================================================================================

Measured as gaps, not listed as tasks.

**The C# tick is still four stubs.** `csharp/Depths.Core/Tick.cs` has the gates, the clocks and the
order, all measured and pinned by `TickOrderTests.cs`, but `tickPlayer`, `tickProjectiles`,
`tickBodies` and `tickRoom` do not exist on the C# side. The JavaScript split into those four
phases this session is the precondition for porting them, and it is now done - so the port has no
structural excuse left, only the work itself. Roughly 1,135 lines of JavaScript to port across four
functions, which is a day of careful work rather than an afternoon, and it is the single largest
outstanding item in the project.

**The `boss` death path is the least-tested branch in the game.** `tickRoom` opens the exit, and
`descend()` reseeds, clears three art caches and rebuilds the floor. The marathon run exercised it
once, end to end, and it worked. Once is not a test.

**No profiling exists for the Unity/`.exe` target.** Every number in this report is a browser canvas
at 1.8% of a 60fps budget. Unity's renderer, its GC and its IL2CPP build are a different machine
with different costs, and none of it can be inferred from here.

**Long-session memory is bounded but not explained.** The sawtooth is healthy; what allocates 8 MB
per cycle is not identified. At this size it does not matter, and if it ever did the number to watch
is that sawtooth's amplitude, not its peak.

## Expectations generated, not written

`RoomPhaseParityTests.cs` was generated from the running game by `tools/room-parity.js`. A
hand-transcribed expectation is only a second opinion about what the code should do; two
implementations of one function disagreeing is a real finding. The generator **reports and does not

generates from, it would simply agree with itself.

16 fixtures, 16 agreements, after three fixture defects were found and fixed.

## Descend measured by dirtying the state

A descent test written from the source lists what the function *appears* to reset, and a line it
appears to reset but does not is invisible. So the browser was put into the dirtiest state it can be
put into - velocity, knockback, spent blinks, a live transition, an armed door, a shell in flight,
every per-floor flag - and then asked to descend. Every value below was read out, not reasoned
about:

    floor 1 -> 2            rootSeed preserved          both clocks zeroed
    cursor -> (3, 3)        player -> (400, 355)        lagX/lagY moved WITH the player
    vx, vy, kvx, kvy -> 0   blinkCharges -> 2           regen -> 0, grace -> 0
    every per-floor flag false                          trans null, armed door cleared
    shells cleared          fade armed at 189 ticks    roomFade 1, state still 'playing'

## Three bugs the tests caught and reading the code did not

**1. `Descend` must NOT clear the pickup list - and my first version did.** In JavaScript a pickup
lives on the ROOM, so descending builds a new dungeon and the old room keeps its contents. Measured:
after a descent from a room holding an exit and a heart, the **old room still holds 2** and the new
start room holds 0.

I read that as "descend must clear the list" and added `pickups.Clear()`, reasoning that this port
keeps the current room's pickups on the RUN rather than the ROOM, so something has to do the job
`rooms[key()]` does for free. The reasoning was sound and the conclusion was wrong. **Clearing is not
what makes a new room empty; replacing the room is.** A descent that clears the run's list is
clearing the *old* room's contents as a side effect of arriving somewhere new. The corrected comment
is in the code and names `enterRoom` as the real gap.

**2. The room phase's mid-function return has to be honoured.** `descend()` already reseeded, moved
the player and rebuilt the dungeon. Falling through would run the death check and the boss-exit check
against a floor the player never saw - and re-opening an exit on arrival.

**3. The exit does not remove itself.** The original calls `descend()` and RETURNS, so the portal is
still in the list on the next tick. My fixture asserted on the list and reported "not collected" for
a distance of **zero** - the exact opposite of what happened. The observable is the floor.

## Still not ported, and it says so

The **item pickup branch** calls `Items.give`, which has no C# counterpart. It throws
`NotSupportedException` rather than stubbing: a silent no-op there is a port that looks finished and
plays differently, and a crash is a gap you cannot miss.

## What the port is actually teaching

Three of the four findings above are the same shape: **the C# model puts state somewhere different
from the JavaScript, and the difference implies a responsibility the original gets for free.** The
pickup list is the clearest case - pickups live on the room in JS and on the run here, so anything
that relied on "new room, empty room" needs an explicit stand-in, and getting that stand-in wrong
produces a bug the original cannot have.

That is the argument for generating expectations rather than writing them. Every one of these was
found by a disagreement, not by reading, and two of the three would have shipped from a green build.

===================================================================================================

`TickOrder.TickPlayer` now carries the whole movement integration. Porting it found a bug in code
that had been sitting in the port for some time.

    JS   237/237   untouched, at all three viewports

## The bug: `TickMomentum` had lost its empty-room guard

The original returns from `tickMomentum` **immediately when the room has no bodies.** Momentum is a
pressure mechanic - it charges from being chased and shot at, and it exists to make that survivable.
The C# port charged it in an empty room, which is a free speed bonus with no counterweight: a player
walking alone gets faster the longer they walk.

**Why it was invisible until now.** Nothing else in the port called `TickMomentum`. No caller, no
test exercising it through the tick, no observable consequence. It became visible the moment
`TickPlayer` landed, because `TickPlayer` *reads* momentum in the same tick - so the wrong value fed
straight back into the acceleration term.

**How it presented.** The acceleration curve read `0.433763` where the game reads `0.433643`. That
is a momentum of **0.0017** - invisible in isolation, obvious as a curve. I spent several rounds
assuming the port's arithmetic was wrong before solving backwards from the numbers and finding the
acceleration ratio `1.00094`.

It is worth stating plainly: this is a defect that a green build carried for as long as the phase was
unported. The test suite passed 185/185 with a mechanic silently inverted in it.

## Two test bugs of my own, from the same investigation

Both are recorded in the test file, because both are repeatable mistakes:

**I asserted the wrong quantity.** The diagonal test claimed the diagonal's *components* equal the
straight line's. They cannot - a normalised diagonal's components are the straight velocity divided
by root two. The property is that the **magnitude** matches, tick for tick, and the measured ratio is
exactly `0.7071067811865476`.

**I counted one tick too many.** The swerve decay read `0.0035` too fast, which read as a rate error
and was a miscount: the meter rises *and* decays on the reversing tick, so the value after tick 1 is
already `0.4365`. Measured over forty ticks the implied rate is `0.0035` exactly.

**And one wrong-condition set.** Some expected deceleration values came from a run with bodies in the
room - where momentum scales the acceleration - compared against an empty-room fixture. Both numbers
are correct for their own conditions. The test now says which is which, because the difference is
real and a reader would otherwise conclude one implementation is wrong.

## What the movement numbers are

Measured in the browser, in an empty room with momentum locked:

    first ten ticks of the ramp   0.16269, 0.306508, 0.433643, 0.54603, 0.645381,

## A design note the port forced into the open

`moveSpeedBonus` is a **parameter** of `TickPlayer`, not a constant read internally. In the original
it is `min(cap, Stats.value('speed') + momentum * MomentumSpeed)` - so it changes with the player's
build. The C# has no stats system yet, so the default is the measured empty-run value and a caller
with a build passes the real one. A phase that read a constant would be correct only for a run
carrying nothing, and would look correct in every test.

That is the fourth time this session that "the port differs in WHERE state lives" has been the actual
subject. It is also the strongest argument for generating expectations: every one of these was found
by a disagreement between two implementations, and two of them would have shipped from a green build.

## Still a stub: `tickProjectiles` and `tickBodies`

160 and 697 lines. `tickBodies` is the largest single piece of work left in the port - pack assembly,
the Brunch shield and rush, the gunner intercept, separation - and it depends on combat, which is
partly ported. `tickProjectiles` is smaller and self-contained apart from damage.

`CheckDoorTransition` is stubbed to geometry only and returns false. That is deliberate: a stub that
guessed would teleport players into the next room, and a crash is a better gap than a wrong room.

# 12. THE PROJECTILE PHASE, MEASURED

# 13. THE PATTERN THAT COST THE MOST TIME
===================================================================================================

Five times in two days, a fixture reported a game defect that did not exist. Each produced a
confident conclusion, several rounds of investigation, and a false trail in the git history.

    the start room's west side is not a wall       its doors are all locked, so a player held
                                                   against it is in a doorway
    momentum reads 0                               tickMomentum returns early on an EMPTY room;
                                                   my fixture had no bodies, so nothing charged
    a diagonal is 0, not 1.4025                    the player was pinned in a corner by the wall
                                                   clamp, so I measured the clamp
    the Brunch does not spare its shooter           the guard check needs `owner` set; a shell with
                                                   no owner is eaten regardless
    an enemy shell does no damage                  playerHit tests the LAGGED hitbox, offset down
                                                   by PLAYER_HIT_DY; I moved x/y but not lagX/lagY

There is a common shape, and it is worth naming precisely:

> **A fixture that does not exercise the code reports success.** Nothing in the output distinguishes
> "the game does not do this" from "my setup never put the game in that situation."

The discipline that actually works, and which every one of these files now carries at the top:

1. **Report coverage with the result.** Enemies seen, rooms entered, floors reached, kills landed,
   projectiles that survived to be examined. A run that tested nothing must be visibly distinct from
   a run that found nothing.
2. **Assert the precondition, not just the outcome.** "The measured distance was 0.00" would have
   caught the `lagX` case instantly. "The player was at 400,300 and the shell was at 402,312 and the
   hit point is 310" cannot be a coincidence.
3. **Capture the bounds at setup.** `ROOM_LEFT` and friends are re-synced per room, so reading them
   after the ticks compares the player against a room it has already left.
4. **Use the game's own helpers.** `spawnEnemy` does not push. The suite already had a helper that
   does; writing a fresh fixture instead of reusing it is how that mistake happened.

The general form: **when a measurement surprises you, check the fixture before you check the game.**
Every single time this session, the surprising measurement was the fixture. Not once was it the game.

# 15. THE BRUNCH RAMP WAS THE WRONG SHAPE
===================================================================================================

Found while porting the Brunch movement, and it is the most consequential measurement of the porting
work.

## What the project believed

    curSpeed = walk * (1 + RAMP_GAIN * min(1, pursuit / RAMP))

which caps at `0.624 * 2.9 = 1.8096`.

## What the game does

Measured with a Brunch in a corner so it never reaches the player:

    tick     1   0.632612        tick  200   1.873043
    tick    50   1.044938        tick  315   2.059271
    tick   100   1.409447        tick  400   2.090368
    tick   157   1.717552        tick  600   2.099676

The curve passes 1.8096 at about tick 190 and keeps going. The real line is

    curSpeed += (runSpeed - curSpeed) * LUNGER_ACCEL * gain

- an **exponential ease toward the run speed**, with the pursuit ramp scaling how hard each tick
pulls. Simulating that line reproduces all ten measured points to six decimal places with zero
difference.

## Two things the wrong formula got right by accident

**It looked fine.** 1.8096 still beats a momentum-full player at 1.6045, which is the whole reason the
bomb-rush is tuned to 2.1. So the wrong formula would have passed any test that asked "does a pack
catch a moving player" - the question that motivated the tuning. The difference is 0.29 of speed on
the mechanic the entire Brunch design hangs off.

**The C# suite asserted the shape, not the numbers**, and so agreed with itself. That is the same
failure as `SwerveDecay` and `BrunchRamp` in the same file: something true in form and wrong in
value, sitting in the place the game's tuning lives.

## Two consequences, now pinned

- **The pack never arrives.** At 600 ticks it is 2.099676, not 2.1. The shortfall shrinks forever, so
  a Brunch at full pursuit is always very slightly slower than its stated run speed.
- **Walk speed is only the starting value.** Change it and the whole curve moves; change the ramp
  gain and the curve changes how fast it gets there. The wrong formula tied the ceiling to the walk
  speed, which is why it capped where it did.

Nine `[TestCase]` rows pin the curve tick by tick. Mutation-checked: substituting the old formula
fails all nine.

## The general point

This is the third constant-shape defect in `Balance.cs` and the first that survived a *deliberate
tuning change* rather than a transcription. The ramp was changed from 2.2s to 1.5s during this
session, and the port kept the old number. Nobody noticed because nothing read it.

Which is why the constant audit is now a gate step rather than a script somebody remembers to run:
it compares 47 constants by value whether or not a caller exists, and it is verified to fail with the
constant named and both values printed.

## THE GAME WAS SILENT. IT HAD BEEN SILENT THE WHOLE TIME.

Reported as: *"the game still does not play any sound."* Not "the sound is quiet", not "the mix is
wrong". **No sound.** And the sound system in this repo had twelve working voices, verified waveforms,
a twenty-decibel-correct mix, a bounded pool, and a 4,200-tick fight test that asserted voices
envelope and release correctly.

All of it was true. None of it was reachable.

### The proof that it was not working

A real browser, Edge, **no autoplay flag** — which is what a player's browser has. A real keydown, a
real click, a real held key with the mouse down:

```
at load        ctxState 'suspended'  unlocked false   blockedByPolicy true
after D        ctxState 'suspended'  unlocked false
after click    ctxState 'suspended'  unlocked false
40 shots       played 40   skippedLocked 40
held D firing  played 50   skippedLocked 50
```

Fifty sounds triggered. Fifty skipped. The counter that would have said so is one nobody reads, and it
is `skippedLocked` — a name that reads like a mute.

### Why every measurement said it worked

Because every measurement in this project launched the browser with
`--autoplay-policy=no-user-gesture-required`. That flag does not fix the game; it *replaces the
browser's policy with one that agrees with the bug*. Same page, same build, flag on: `ctxState
'running'`, every assertion passed, the fight test green.

There is a lesson in this that costs more than the bug did, and it generalises past audio:

> **A harness that relaxes the policy under test is not testing the policy.** The flag was added to
> make audio benchmarks possible, and it made them measure a browser that does not exist.

The frame-time probes, the tick profiler, and all four waveform benchmarks were run under it. The tick
and render numbers are still valid — they do not involve the autoplay policy. Every *audio* number
was not.

### The bug, in three parts, each of which alone would have been survivable

**1. The context was built at load, before any gesture.**

`Sound.autoUnlock()` is called at module scope from `80-ui.js`, and it claimed a gesture it had not
received. So an `AudioContext` was constructed with no user interaction — which is precisely and only
what every browser's autoplay policy suspends. The context came up `suspended`. Verified in isolation:
a raw `new AudioContext()` with no game code at all also comes up `suspended` on this machine.

**2. `resume()` returns a promise, and the state was read before it settled.**

```
ctx.resume();                    // returns a Promise
unlocked = (ctx.state === 'running');   // read on the NEXT LINE
```

The state does not change until the promise settles. So `unlocked` was false on a context that was
about to run, and every voice in the game took the `skippedLocked` path.

**3. The guard made both of the above permanent.**

`unlock()` began `if(ctx || !Ctor) return false;` — and `ctx` had just been assigned, three lines
above. So the **first** gesture produced a context it could not resume, and every gesture after that
returned immediately without attempting anything. The listeners were only removed on success, so they
stayed installed, calling a function that could not succeed. There was no path from the broken state
back to sound, short of reloading the page.

That third part is why this survived. Parts 1 and 2 produce a game that is silent for one gesture and
then self-corrects. Part 3 is what made it silent for ever.

### The fix

- No context is constructed until a real gesture. `autoUnlock()` now distinguishes registration
  (load, no event) from unlocking (an event), and the load-time call only installs listeners.
- `resume()` is awaited, and the state is read after it settles. The synchronous read is kept
  alongside, because a context that is already running must not cost a frame of silence.
- A suspended context is **resumable, not fatal**. The guard is now `if(!ctx) return false` — no
  context genuinely means no audio, and that case still refuses. A context in the wrong state gets a
  `resume()` on the play itself.
- `play()` asks the *context*, not the flag, and the flag is only a fast path.
- `stats()` derives `unlocked` from `ctx.state` rather than reporting a stored flag that `play` can
  set independently — so a test reading it reads the truth.

### What this also fixed, which I did not go looking for

A player who alt-tabs mid-fight and comes back was left with a permanently muted game, because the
original hard gate `if(!unlocked || !ctx || ctx.state!=='running')` refused to play on a suspended
context and only a gesture could resume it. The same line was the autoplay bug's accomplice and this
second, entirely separate failure. One line, two ways to be silent.

### Measured after the fix

Same probe, same browser, same absence of any autoplay flag:

```
at load        ctxState 'none'      — no context built, which is correct
after D        ctxState 'running'   unlocked true
40 shots       played 40   skippedLocked 0   voices 48
held D firing  played 50   skippedLocked 0
```

### THE TEST THAT COULD NOT FAIL

The two regression tests took a long time to come right, and the reason is worth more than the fix.

I added three serial audio tests. All three reported `ok`. The suite reported `239/239`. Then I
restored the **original permanent-silence guard** into `play` - the exact line that caused this bug -
and re-ran.

**240/240. The mutation survived.**

Not "the test was weak". The test body never executed. The dispatch was:

```js
const r = serial ? null : invoke2();
if (r && r.then) { /* run it, race the watchdog */ }
else             { results.push({name, ok:true, asserts:n}); }   // <- serial tests landed here
```

For a serial test `r` is `null` **by design** - that is what serialising means. So the condition was
false, so control fell to the `else`, which pushes a pass. Three tests - including the two written
specifically to catch a permanently silent game - were counted in the total, included in the pass
count, and **structurally incapable of failing**.

The tell, which I should have read as a failure rather than as a number: `asserts=0`. `asserts` is a
module-level counter shared by every test, so a test that never ran still reported a large number -
until the serial path was fixed and each of the three reported `asserts=0` while still claiming `ok`.

Three lessons, all of which cost an hour between them:

> **A green count is not evidence that the check ran.** This is the fixture rule this project has now
> learned six times, and this instance is the purest: the fixture did not merely mislead, it did not
> exist.
>
> **`r` is not the question "is this test done".** `r` only exists for a test that was allowed to
> start. The flag is the question. Branching on `serial` first is the whole fix.
>
> **A helper that repairs the state under test deletes the test.** An earlier version called
> `await Sound.whenAudible()` immediately after the gesture. `whenAudible` sets `unlocked` itself - so
> it repaired the exact state the test was checking, and the broken guard passed.

### `requestAnimationFrame` does not fire inside this harness

Fixing the dispatch made the three serial tests actually run, and immediately the suite hung at 236.
The cause is worth recording because the symptom pointed nowhere near it:

- The suite runs its test bodies **while the page is still parsing**, so the main thread is blocked.
- `requestAnimationFrame` is not delivered until the browser regains control. It never does while the
  suite is on the stack.
- So `waitForFunction` - which polls with rAF by default - never ran its predicate, and Playwright
  reported **"Timeout 30000ms exceeded" with an empty call log**.
- `{polling: 500}` did not help: with an explicit interval Playwright still applies its own budget.
- `waitUntil:'load'` and then `waitUntil:'domcontentloaded'` both timed out too, for the same reason.

Four separate runner-level timeouts all reported as *page* failures. The audio helpers `whenAudible`
and `whenIdle` were built on rAF and could not complete either - which is why they kept returning
`false` and why the tests kept failing against correct code.

The fixes: the helpers yield with `setTimeout(1)`, both runners use a plain poll loop with their own
deadline, and the wait budgets are now in **milliseconds** rather than frame counts - because
`if(++frames>30)` meant "thirty milliseconds" once a frame stopped being a frame, and gave up before the
promise it was waiting for could settle.

The suite now takes about 200 seconds instead of about 60. That is the honest cost of three tests that
share one `AudioContext` and one voice pool with 236 tests running at once, and the serial watchdog is
raised to 240s to match - a watchdog that fires on correct code has stopped being a watchdog.

### A harness that reports pass counts and ignores exceptions is blind by construction

`run.js` had no `pageerror` listener. It now has one, and it prints on every run whether or not
anything failed - because a page can be `239/239` and still have thrown on the way there. The listener
found a one-line fault in a single run that four suite runs had missed: a test hook calling `suspend()`
on an **`OfflineAudioContext`**, whose `suspend()` requires an argument and threw a `TypeError` that
escaped into another test's render.

### The two regression tests, and what they cost

`audio is not built until a gesture, and a gesture makes it work` and `a suspended audio context can
always be brought back`. Both mutation-relevant: restoring `if(ctx) return false` fails the second;
restoring the load-time context build fails the first.

Getting them to pass honestly took four runs, and **every one of the four failures was the fixture,
not the game** — this project's oldest lesson, learned a fifth time:

1. Asserted the precondition `ctxState !== 'suspended'`. The suite runs its 239 tests
   **concurrently**, so 100 others had already dispatched synthetic keydowns and built a context. Not
   evidence of anything.
2. Checked state synchronously after `resume()` — the same mistake the original bug made.
3. `serial` was both a function name and a parameter name, so the queue was `undefined`.
4. With the three audio tests serialised, they still failed — because a neighbour's offline `render()`
   holds the `rendering` lock and `play()` correctly refuses during a render. The tests needed
   serialisation *and* to not race a render.

So the harness grew a serial queue (`test(name, fn, true)`) for tests that share one piece of global
state, and the failure message now carries the whole of `stats()` — because "a shot did not play" is
the least useful sentence available when `play` can decline for four different reasons, and three of
them are not this bug.
